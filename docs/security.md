# Security

This is the threat model, the controls we require, and how to check them. Any change that touches auth, data access, uploads, HTML rendering, or the practice partner must keep every control here intact and tested.

## Assets

1. **User accounts:** credentials and sessions.
2. **Student personal data:** name, email, school, major, résumé PDFs, practice transcripts and scores.
3. **Employer data:** company profile, job drafts, applicant pipeline.
4. **LLM provider keys and spend.**
5. **Integrity of public job listings** (scam jobs, phishing links).

## The static demo

The GitHub Pages site ([deploy.md](deploy.md#github-pages-demo)) is files only, so the controls in the table that live in the api, in sessions, cookies or CSRF tokens, or in the coach's HMAC check have nothing to protect there: the demo has no accounts, stores nothing on a server, and the practice partner runs in the visitor's browser, where the only data is the visitor's own. What changes:

- **Headers.** A static host sets none, so the document carries `<meta http-equiv="Content-Security-Policy">` with `default-src 'self'`, `script-src 'self' 'unsafe-inline'`, `style-src 'self' 'unsafe-inline'`, `img-src 'self' data:`, `font-src 'self'`, `connect-src 'self'`, `base-uri 'self'`, `form-action 'self'` and `object-src 'none'`. Static HTML has no per-request nonce, so Next's inline bootstrap needs `'unsafe-inline'`; `'unsafe-eval'` stays out, and `connect-src 'self'` means the page can call nothing but its own origin. `frame-ancestors`, HSTS, `X-Content-Type-Options`, `Referrer-Policy` and `Permissions-Policy` cannot be set from a page and are missing on the demo. The e2e suite for the export (`npm run e2e:pages`) fails on any CSP violation in the console.
- **Cookies and CSRF.** The export never sets or reads a cookie: the root layout does not read the session cookie, `apiFetch` and `apiStream` answer from the browser (`apps/web/lib/demo`), and no CSRF token is fetched. Session state is `sessionStorage` for the tab.
- **The partner.** The same guard rules, canary check, output check and PII redaction run, in the browser, on the visitor's own text; the hidden part of a scenario is in the tab's storage because the partner that needs it runs there. The scripted provider makes no network calls.
- **Robots.** `robots.txt` is generated under `/PitchPerfect/`, where crawlers do not look for it; the `noindex` metadata on the account routes still applies to the note pages they render.

## Age and consent

- Students confirm they are 18 or older at sign-up (`ageConfirmed: true` is required and stored as `ageConfirmedAt`).
- Before the first practice session, students accept the practice notice. It says three things:
  - The partner is an AI. When the coach runs `COACH_PROVIDER=fake`, the api reports `practicePartner: "scripted"` on `/api/health` and `/api/practice/quota`, and the notice, the persona badge, and the privacy and terms pages say instead that the partner is a scripted demo running on our server and that nothing is sent to an AI provider. A coach that is down or unknown is disclosed as live.
  - Transcripts are processed by the configured LLM provider and kept for 180 days (`PRACTICE_RETENTION_DAYS`; the copy reads the shared default, see docs/deploy.md).
  - The browser's speech recognition may send audio to the browser vendor (Google, Apple or Microsoft). PitchPerfect never receives or stores audio.
- Acceptance is stored as `practiceConsentAt`.

## Logging

- Use structured JSON logs (`pino`). Request lines come from `pino-http` and carry `requestId`, `route` (the matched pattern, never the raw URL), `req.method`, `res.statusCode` and `responseTime` (ms). Practice lines add `attemptId`, `stage`, token counts and `outcome`.
- Never log bodies, headers containing cookies or authorization, transcripts, tokens, or file contents.
- `pino` redaction paths cover `req.headers.cookie`, `req.headers.authorization`, `*.password`, `*.token`, `*.text`.

## Reporting

Found a vulnerability? Please open a private security advisory on the GitHub repository, or email the maintainer listed on the GitHub profile. Do not open a public issue. Expect an acknowledgement within 72 hours.

## Pre-release security checklist

- [ ] `npm audit --audit-level=high` is clean in all workspaces
- [ ] gitleaks reports no findings across the full history
- [ ] Every api route has unauthenticated, wrong-role, and not-owner tests
- [ ] All XSS and NoSQL-injection payload tests pass
- [ ] With a real `COACH_PROVIDER`: `npm run eval -w apps/coach` run once against the production model ids, pass rate recorded, every adversarial case handled (docs/deploy.md step 6). Not applicable to a `fake` (scripted) deployment
- [ ] Response headers are verified on the deployed preview (CSP, HSTS, nosniff, frame-ancestors)
- [ ] `.env.example` files contain no real values
